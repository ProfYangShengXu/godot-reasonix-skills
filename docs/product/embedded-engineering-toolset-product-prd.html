1. 背景与目标

现实问题

嵌入式开发是软件工程中最碎片化的领域——每个芯片平台有自己的工具链（IDE、编译器、烧录器、调试协议）、自己的 SDK、自己的寄存器手册、自己的踩坑经验。一个 MCU 工程师换一颗新芯片的"上手指南"时间通常以周计算。

现有的 AI 编程助手（Copilot、Cursor、Reasonix）擅长通用软件（写 React、调 API、写 Python），但在嵌入式领域寸步难行——它们不知道 OpenOCD 的配置文件格式、不会算分频系数、不认识 CMSIS-DAP 和 J-Link 的区别。结果是：嵌入式开发者仍然对着十几份 PDF 手册手动配寄存器，AI 帮不上忙。

一句话定位

"面向嵌入式全栈的 AI Agent 工具箱 — 每个角色一个技能卡，Agent 按需加载角色能力。"

现存方案痛点

  • IDE 学习成本极高：STM32CubeIDE、Keil MDK、IAR、Vivado、Quartus……每个工具都有自己的界面和配置逻辑
  • 官方文档分散且版本敏感：一份 HAL 库手册 2000+ 页，且不同芯片版本有细微差异
  • 烧录/调试命令与硬件绑定：OpenOCD、J-Link Commander、ST-Link CLI、pyOCD——命令参数随调试器、目标芯片、OS 变化
  • 工程师需要同时懂 MCU、FPGA、Linux、电力电子：知识面太广，没人能全记住
  • 现有 AI 工具在嵌入式领域"失语"：不知道 CubeMX CLI 的参数、无法理解 .ioc 文件格式

4. MVP 定义

Must-have（优先级排序）

  1. P0 角色系统框架：16 个角色卡（SKILL.md）独立存储，角色名片 + AI 指令 + 工具链引用，嵌入式架构师角色可编排子角色
  2. P0 MCU 固件工程师：CubeMX2 CLI 调用 → HAL 代码框架生成 → Keil/IAR/ARM GCC 编译 → OpenOCD / J-Link 烧录
  3. P0 FPGA 工程师：Verilog/VHDL Testbench 生成 → ModelSim/Questa 仿真 → 自动比对波形 → Vivado/Quartus 综合下载
  4. P0 硬件信号查询引擎：搜索芯片数据手册 → 提取寄存器地址/引脚定义/时序参数 → 以结构化表格呈现
  5. P0 安装示例文档：每角色附带面向零基础用户的安装指引（含软件下载地址、环境变量设置、首次运行验证）
  6. P1 Linux 应用/驱动工程师：交叉编译工具链配置 → Device Tree 编辑 → Kernel Module 编译 → scp/tftp 部署到目标板
  7. P1 烧录/调试统一接口：抽象 OpenOCD、J-Link、ST-Link、DAP-Link、pyOCD 为统一 CLI 命令
  8. P1 QT/C++ 编译工程支持：qmake/cmake 构建 → 交叉编译 → 部署到目标板

Nice-to-have（二期）

  • P2 电源工程师/射频工程师：LTspice 仿真 + S 参数分析 + PCB 阻抗匹配检查
  • P2 功能安全工程师：MISRA-C 检查 + 安全分析报告自动化
  • P2 模型量化部署工程师：TensorFlow Lite / ONNX → MCU/边缘 NPU 部署流水线
  • P2 BMS 软件工程师：电池 SOX 算法验证 + BQ76952/ADBMS 等芯片驱动模板
  • P3 CI/CD 集成：GitHub Actions 一键 STM32/FGPA 编译 + 仿真回归

🚫 明确不做什么

  • 不做 硬件原理图自动设计（让 AI 画电路图）—— 这需要电气工程 AI 训练，超出范围
  • 不做 实时操作系统调度器实现 —— 只封装 FreeRTOS/Zephyr 的配置和 API 调用
  • 不做 代做竞赛/考试题目 —— 工具集提供方法，由用户自己完成
  • 不做 PCB Layout 自动布线 —— 保留 AI 建议但最终由人在 EDA 中操作
  • 不做 任意芯片支持 —— 一期只覆盖 STM32F/H/G 系列 + ESP32 + 通用 FPGA (Cyclone IV/V, Artix-7)

6. 竞争分析与 SWOT

竞争格局

竞品/替代方案定位优势劣势与本产品差异
STM32CubeMX GUI ST 官方图形化配置工具 官方支持，引脚可视化，冲突检查完善 需手动操作 GUI，不能被 AI 脚本调用（CLI 功能有限） 本工具把 CubeMX CLI 暴露给 Agent，可脚本化
PlatformIO 嵌入式开发统一平台 统一 CLI，多框架支持，库管理方便 配置格式固定，不支持高级调试、自定义 Linker Script、非标准烧录器 角色化处理不同工具链，更灵活
OpenOCD + custom scripts 开源调试/烧录工具 灵活，支持多平台 配置复杂，每次换芯片要重写配置文件 封装成统一接口，根据芯片型号自动选配置
厂商 FAE 支持 芯片厂商技术支持 专业，官方权威 响应慢（几天），不覆盖非官方方案 即时响应，24/7 可用

SWOT 分析

S 优势

  • 已有 NUEDC Skills 项目中 7 个技能的成功实践和社区验证
  • 16 个角色覆盖嵌入式全链路，填补 AI 在嵌入式领域的空白
  • 每个角色独立存储，可按需加载不冲突
  • 面向"什么都不懂的用户"的安装文档是其独特竞争力

W 劣势

  • 团队规模小（作者个人），维护 16 个角色需要大量精力
  • 嵌入式工具链版本碎片化严重（Keil 5.38 vs 5.39 就有差异）
  • 依赖第三方闭源工具（Keil、Quartus、Vivado）——这些工具无法开源分发
  • 缺乏真实的硬件测试环境覆盖所有芯片组合

O 机会

  • AI Agent 生态爆发：Reasonix、Cursor、Claude Code 都在探索垂直领域
  • 嵌入式领域 AI 工具几乎空白，是蓝海市场
  • RISC-V 生态崛起带来更多碎片化需求
  • 高校电赛/机器人赛每年有数万参赛者急需降低工具链门槛

T 威胁

  • ST/ARM/AMD 等大厂可能推出自己的 AI 编程助手（官方集成优势）
  • 嵌入式开发者对 AI 的信任度不高——"烧录不能出错"的零容忍心态
  • 工具链版本更新可能破坏已有角色配置
  • 竞品快速跟进——嵌入式 AI 辅助的门槛主要在知识积累，不是技术壁垒

7. 设计理念

体验关键词

角色即文档 可组合 零环境门槛 确定性输出

  • 角色即文档：每个角色一张独立的 SKILL.md，包含：身份卡、能力范围、工具链路径、常见操作指令、踩坑 FAQ。Agent 加载角色即获得该领域能力。
  • 可组合：嵌入式架构师角色可编排子角色——例如"用 MCU 固件工程师生成代码，再调用 BSP 工程师写 Linux 驱动"。
  • 零环境门槛：每个角色都配一份面向"什么都不懂"的安装文档——软件哪里下载、环境变量怎么设、验证命令是什么。
  • 确定性输出：烧录、编译、仿真操作必须输出完整 stdout/stderr 和退出码，不靠 AI 猜测。

核心交互原则

  1. 用户说场景，Agent 选角色。用户不需要知道哪个角色负责什么——描述问题（"我要烧录 STM32F407 的程序"），Agent 路由到对应角色。
  2. 先查手册，再操作。涉及硬件寄存器、引脚号、时钟频率的操作，必须先搜索官方文档，不能凭记忆。
  3. 安装即验证。每个工具链的安装完成后，必须运行一条验证命令确认可用。

视觉风格

这是 AI Agent 技能集，不是用户界面产品。无传统 GUI。

  • 终端输出：工业感灰底白字，绿色 CHECK / 红色 FAIL
  • 文档排版：参考 ST/STM32 官方文档风格——清晰的分层编号 + 表格化参数说明
  • 角色命名：中文职业名称 + 英文标识符（如 stm32-firmware-engineer），确保机器可读

8. 风险

风险类别风险描述可能性影响缓解措施
市场风险 目标用户群太小——需要 AI Agent 工具 + 做嵌入式开发的交集 中 高 先用 NUEDC（电赛）场景验证产品-市场匹配；电赛每年数万参赛者是最直接的种子用户
