# docs — 产品设计文档

**语言指令：推理用英文，回复用中文。**

## 核心原则

```
本 skill 只回答 WHAT 和 WHY，不回答 HOW。
不写一行代码、不画一张架构图、不定一项技术栈。
HOW 由 pipeline 架构师负责。
```

## 产出物

1. `docs/product/<项目名>-product-prd.html` — 产品设计文档（浏览器打开，给人读的）
2. `docs/product/<项目名>-product-prd.yaml` — 结构化产品定义（机器可读，pipeline 架构师直接引用）

两个文件必须同时产出，内容一致。

---

## 🎨 HTML 样式规范

产出的 HTML 必须内嵌 CSS，使用以下风格：

```
- 深色标题栏（#1a1a2e 或类似深色）+ 浅色内容区（#f8f9fa）
- 响应式布局：桌面优先，移动端（≤768px）可读，使用 @media
- 可折叠章节：用 <details><summary> 包裹每个大节
- 粘性目录导航（sticky sidebar）：左侧或顶部，点击跳转锚点
- 打印友好：@media print 隐藏导航、折叠展开、缩小边距
- 表格：交替行颜色、左对齐表头
- 代码风格：项目名、文件名用等宽字体
- 顶部显示生成时间和版本标记
```

## HTML 必须包含

### 1. 背景与目标

- 这个产品解决什么**现实问题**？
- **一句话定位**是什么？（像 Airbnb for X / 类 Notion but for Y）
- 现存方案有什么痛点？

### 2. 数据指标（OKR 体系）

定义可量化的成功标准：

| 层级 | 指标 | 目标值 | 衡量方式 |
|------|------|-------|---------|
| North Star | 北极星指标 | 例如"周活跃项目数 ≥ 1000" | 埋点/日志 |
| KR-1 | 关键结果 1 | 量化的里程碑 | 具体统计方式 |
| KR-2 | 关键结果 2 | 量化的里程碑 | 具体统计方式 |
| KR-3 | 关键结果 3 | 量化的里程碑 | 具体统计方式 |

**原则**：每个 KR 必须可量化、有时间限制、能直接反映产品价值，不是 vanity metric。

### 3. 用户画像（至少 3 类）

每类用户使用**固定表格模板**：

| 维度 | 画像 A：<名称> | 画像 B：<名称> | 画像 C：<名称> |
|------|---------------|---------------|---------------|
| 身份/场景 | | | |
| 核心痛点 | | | |
| 使用频率 | | | |
| 核心诉求 | | | |
| 技术熟练度 | | | |
| 替代方案 | | | |

**要求**：画像必须有真实感（有具体的身份和场景描述），不准用"普通用户"、"高级用户"这种模糊标签。

### 4. MVP 定义

- MVP 必须包含的功能（must-have），按优先级排序
- 一期后加的功能（nice-to-have）
- **明确不比什么**——说出来不做什么比做什么更重要

### 5. 2B / 2C 分析

| 维度 | To C | To B |
|------|------|------|
| 用户是谁 | | |
| 付费意愿 | | |
| 决策链 | | |
| 核心功能差异 | | |
| 获客方式 | | |

如果两个都有，说明主次关系和功能分区。如果只做一端，说明理由。

### 6. 竞争分析与 SWOT

#### 竞争格局矩阵

| 竞品 | 定位 | 目标用户 | 优势 | 劣势 | 与本产品差异 |
|------|------|---------|------|------|------------|
| 竞品 A | | | | | |
| 竞品 B | | | | | |
| 竞品 C | | | | | |

至少列出 3 个竞品或替代方案（包括非数字替代——比如"用户现在用 Excel 做"也算）。

#### SWOT 分析

| | 正向 | 负向 |
|--|------|------|
| **内部** | **S（优势）**：团队/技术/资源上的独特优势 | **W（劣势）**：团队/技术/资源上的短板 |
| **外部** | **O（机会）**：市场/政策/技术趋势带来的机会 | **T（威胁）**：竞品/政策/市场变化带来的威胁 |

### 7. 设计理念

- 体验关键词（"极简"、"专业"、"有趣"、"可靠"）
- 核心交互原则（不超过 3 条）
- 视觉风格方向（文字描述，不需要设计稿）

### 8. 风险（非技术）

| 风险类别 | 风险描述 | 可能性 | 影响 | 缓解措施 |
|---------|---------|-------|------|---------|
| 市场风险 | 竞品抢先发布 / 需求不存在 | 高/中/低 | 高/中/低 | |
| 运营风险 | 内容审核 / 法规合规 / 本地化 | 高/中/低 | 高/中/低 | |
| 增长风险 | 冷启动困难 / 用户获取成本高 | 高/中/低 | 高/中/低 | |
| 变现风险 | 付费意愿不足 / 定价策略失误 | 高/中/低 | 高/中/低 | |

## YAML 副产物格式

`docs/product/<项目名>-product-prd.yaml` 必须包含以下字段：

```yaml
product:
  name: "<项目名>"
  one_liner: "<一句话定位>"
  created_at: "<生成时间 ISO-8601>"

success_metrics:
  north_star: "<北极星指标>"
  key_results:
    - name: "KR-1"
      description: "<描述>"
      target: "<量化目标>"
      measure: "<衡量方式>"
    - name: "KR-2"
      description: "<描述>"
      target: "<量化目标>"
      measure: "<衡量方式>"
    - name: "KR-3"
      description: "<描述>"
      target: "<量化目标>"
      measure: "<衡量方式>"

personas:
  - name: "<画像名称>"
    scenario: "<身份/场景>"
    pain_point: "<核心痛点>"
    frequency: "<使用频率>"
    need: "<核心诉求>"
    tech_level: "<技术熟练度>"

mvp:
  must_have:
    - "<功能1>"
    - "<功能2>"
  nice_to_have:
    - "<功能3>"
  out_of_scope:
    - "<明确不做>"

competitors:
  - name: "<竞品名称>"
    positioning: "<定位>"
    strength: "<优势>"
    weakness: "<劣势>"
    difference: "<与本产品差异>"

swot:
  strengths:
    - "<优势1>"
  weaknesses:
    - "<劣势1>"
  opportunities:
    - "<机会1>"
  threats:
    - "<威胁1>"

risks:
  - category: "<类别>"
    description: "<描述>"
    likelihood: "<高/中/低>"
    impact: "<高/中/低>"
    mitigation: "<缓解措施>"
```

YAML 内容的字段数量和 HTML 保持一致。HTML 为主（给人读），YAML 为辅（给架构师用）。
